# Alloy Releasing & Distribution Guide

This document outlines the release process, versioning policies, distribution channels, code signing configurations, and verification procedures for Alloy.

#### Release notes on GitHub

Each release page is generated by `scripts/release-notes.sh <tag>`, run by the `create-release` job of
`release.yml` (it also refreshes the notes when a run is repeated): the matching section of
`CHANGELOG.md` as **Highlights**, every commit since the previous version grouped by type with links
(git-cliff + `cliff.toml`; `chore(release)` bumps are skipped), a **Full changelog** compare link
(`compare/vPREV...vTAG`) and the install notes from `.github/release-notes.md`. Write the CHANGELOG
section before tagging and keep commits conventional so the list reads well. To preview or refresh an
old release by hand: `scripts/release-notes.sh v0.1.5 | gh release edit v0.1.5 --notes-file -`.

---

## 1. Versioning Strategy

Alloy follows [Semantic Versioning (SemVer 2.0.0)](https://semver.org/) and [Conventional Commits](https://www.conventionalcommits.org/):

- **Pre-1.0 (Phase P1–P4):** `0.MINOR.PATCH`
  - `0.MINOR`: Incremented on significant feature milestones, breaking API changes, or protocol revisions.
  - `PATCH`: Incremented on bug fixes, performance optimizations, and backward-compatible improvements.
- **Post-1.0:** Strict `MAJOR.MINOR.PATCH` SemVer guarantees.

### Changelog Generation via `git-cliff`

Alloy uses [`git-cliff`](https://git-cliff.org/) configured via `cliff.toml` to generate structured changelogs directly from Conventional Commits.

#### Installation
```bash
# macOS (Homebrew)
brew install git-cliff

# Cargo (any platform)
cargo install git-cliff
```

#### Usage via `just`
```bash
# Preview unreleased changes since last tag
just changelog --unreleased

# Generate or update CHANGELOG.md for a release
just changelog -o CHANGELOG.md

# Prepend changes for a new release version
just changelog --tag v0.1.0 -o CHANGELOG.md
```

## 2. Release Channels

| Channel | Trigger | Signing | Target Artifacts | Destination |
|---|---|---|---|---|
| **Nightly** | Daily at 02:00 UTC or `workflow_dispatch` | Unsigned desktop; Debug APK | macOS (arm64 + x64), Windows x64, Linux (AppImage + deb), Android debug APK | Rolling GitHub Prerelease (`nightly`) |
| **Stable** | Git tag push `v*` (e.g. `v0.1.0`) | Signed (stable self-signed identity or Apple Developer ID) | macOS DMG/App (signed; notarized only if Apple ID configured), Windows NSIS/MSI, Linux deb/AppImage, Signed Android APK | GitHub Releases (Draft -> Published) |

### Nightly Version Metadata
Nightly builds append commit metadata to the base version per SemVer 2.0.0:
```
0.1.0-nightly+<commit>.<describe>
# Example: 0.1.0-nightly+75ddfff.75ddfff
```
This is injected into `apps/alloy/src-tauri/tauri.conf.json` by `scripts/embed-nightly-version.mjs` before packaging.

## 3. In-app updates (OTA)

**Desktop** (macOS, Windows, Linux) uses Tauri's updater plugin. The app checks periodically
(setting "Automatically check for updates") and shows an "Update" button in the title strip.
With "Download updates automatically" the package is downloaded in the background; the button then
reads "Restart to apply update". The package is verified against the minisign public key compiled
into the app before it is installed. Updates only ever come from tagged releases (`v*`), never from
nightlies.

App commands (`apps/alloy/src-tauri/src/update.rs`):
- `check_update() -> UpdateInfo { available, version, notes, can_install, url, downloaded }`.
  `downloaded` is true when the package for that version is already stored in memory. Checking the
  same version again keeps the stored package; a different version drops it.
- `download_update()`: downloads and verifies the offered update without installing it. Emits
  `update://progress` (`{ downloaded, total }`, total is `null` when unknown) while downloading and
  `update://downloaded` (no payload) once the package is stored. Serialized: a concurrent call waits
  for the first download. Errors when no update is offered or the platform cannot install.
- `apply_update()`: installs the offered update (downloading it first if needed) and restarts the app.

`notes` in `latest.json` is the release notes markdown shown in the in-app changelog. The release
workflow fills it from the GitHub release body, so write the release page notes for users.

**Android** cannot replace its own APK, so `can_install` is false: the app only tells the user a
newer release exists, shows the notes, and opens the release page (`check_update` reads the GitHub
releases list); `download_update` and `apply_update` return an error. Silent in-place
updates need a store (Play, F-Droid) or a privileged installer. Updating the sideloaded APK also
requires the same signing key every time, see section 5.

### How the feed works
1. Pushing a `v*` tag runs `release.yml`. `tauri-action` builds each platform, signs the
   updater packages with `TAURI_SIGNING_PRIVATE_KEY` and uploads them plus a merged `latest.json`
   to that release.
2. `publish-update-feed` copies `latest.json` to the fixed `updater-feed` release.
   The app reads `https://github.com/centopw/alloy/releases/download/updater-feed/latest.json`.
   (GitHub's `releases/latest/download/` URL skips pre-releases, so it cannot be used while
   releases are pre-releases.)
3. The app version lives in one place, `version` in `apps/alloy/src-tauri/Cargo.toml`. Tauri and
   `tauri-action` read it from there (`tauri.conf.json` and `ui/package.json` carry no version, and the
   release gate fails if one reappears), so installed apps see a newer version as soon as that line is
   bumped and tagged.

### Keys
- The key pair was generated with `pnpm tauri signer generate -w ~/.alloy-updater/alloy.key`.
  The public key is in `tauri.conf.json` (`plugins.updater.pubkey`).
- The private key and its password are GitHub secrets `TAURI_SIGNING_PRIVATE_KEY` and
  `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`. **Back up `~/.alloy-updater/` somewhere safe.** If the
  private key is lost, installed apps can never be updated again (they only trust that key);
  users would have to reinstall a build that carries a new public key.
- Rotating the key means shipping one release signed with the old key that contains the new
  public key.

### Testing an update locally
Build two versions with `TAURI_CONFIG` overriding `version` and pointing
`plugins.updater.endpoints` at a local server (`dangerousInsecureTransportProtocol: true`), serve a
`latest.json` whose signature is the `.sig` of the newer `.app.tar.gz`, and start the older app.
This was done on macOS arm64 (0.1.0 to 0.1.1): manifest fetched, package downloaded, signature
verified, bundle replaced, app restarted as 0.1.1.

## 4. Required CI/CD Secrets

The following GitHub Actions secrets must be configured in repository settings:

### Desktop Code Signing & Notarization
| Secret | Description | Target Platform |
|---|---|---|
| `APPLE_CERTIFICATE` | Base64-encoded Developer ID Application or self-signed `.p12` certificate | macOS |
| `APPLE_CERTIFICATE_PASSWORD` | Passphrase for the `.p12` file | macOS |
| `APPLE_SIGNING_IDENTITY` | Identity string (`Alloy Release Signing` or `Developer ID Application: Name (TEAMID)`) | macOS |
| `APPLE_ID` | Apple ID account email used for notarization | macOS |
| `APPLE_PASSWORD` | App-specific password generated on appleid.apple.com | macOS |
| `APPLE_TEAM_ID` | 10-character Apple Developer Team ID | macOS |
| `WINDOWS_CERTIFICATE` | Base64-encoded Authenticode code-signing certificate (`.pfx`) | Windows |
| `WINDOWS_CERTIFICATE_PASSWORD` | Passphrase for the Windows `.pfx` certificate | Windows |
| `TAURI_SIGNING_PRIVATE_KEY` | Minisign private key for Tauri updater manifests | Desktop (all) |
| `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`| Passphrase for the updater private key | Desktop (all) |

### macOS signing identity (self-signed) and the keychain prompt

Alloy stores account session credentials and encryption keys in the macOS login keychain. The macOS Security subsystem restricts access to keychain items based on the application's *code signing identity* and designated requirement ("Always Allow").

#### Why earlier builds prompted on every update
Builds signed ad hoc (`codesign -s -`) have a designated requirement tied directly to the binary's code directory hash (`cdhash H"..."`). Because every build generates a different hash, macOS treated every updated application as a completely distinct, untrusted binary attempting to access another app's keychain items. Consequently, users were forced to re-enter their macOS account password on every single application update.

#### Transition to the stable identity and the one-time "Always Allow" prompt
Releases are signed with a stable self-signed certificate with Subject `CN=Alloy Release Signing, O=Alloy`. All builds signed with this certificate share the exact same designated requirement:
```
identifier "vn.hce.alloy" and certificate root = H"f0dca1b41b0a35fb57bd2120c062e95fa0559963"
```

> Releases up to 0.2.9 were signed with the bundle identifier `chat.alloy` and therefore carried
> `identifier "chat.alloy" and certificate root = H"f0dca1b41b0a35fb57bd2120c062e95fa0559963"`. 0.2.10 renamed the
> identifier to `vn.hce.alloy`, so its designated requirement differs from the one that guards every keychain item
> created by 0.2.9 and earlier. The first 0.2.10 launch shows one macOS keychain dialog; **"Always Allow"** re-binds the
> existing items to the new identity and later updates do not prompt again. The keyring service name stays `chat.alloy`,
> so no secret is lost.

When users upgrade from an earlier ad-hoc signed release (e.g. v0.2.2 / v0.2.3) to the first release signed with this stable identity:
1. macOS detects that the designated requirement changed from the previous ad-hoc `cdhash`.
2. macOS displays a **one-time modal keychain access dialog** asking whether to allow "Alloy" to access the keychain item.
3. The user must click **"Always Allow"** and enter their macOS account password once.
4. Because all subsequent releases retain the identical designated requirement, macOS recognizes the code identity and will **not prompt for the keychain password again** on future updates.

#### CI signing architecture (`release.yml`)
Tauri 2.12.x bundles `tauri-macos-sign`. When `APPLE_CERTIFICATE` and `APPLE_CERTIFICATE_PASSWORD` are exported in the environment, `tauri-macos-sign` attempts to parse an official Apple Developer ID certificate by searching for Apple prefixes (`Developer ID Application:`, etc.) and extracting a 10-character Apple Developer Team ID from the certificate's `Organizational Unit` (OU) field. A self-signed certificate lacks an Apple Team ID, causing `tauri-macos-sign`'s `identity::list` to fail with `failed to resolve signing identity`.

When `APPLE_CERTIFICATE` is absent from the environment but a signing identity is configured, Tauri instead delegates code signing directly to `/usr/bin/codesign` using the default user keychain search list.

To resolve this robustly, `.github/workflows/release.yml` routes signing depending on whether `APPLE_ID` is configured:
- **Self-signed path (`APPLE_CERTIFICATE` set, `APPLE_ID` absent):**
  - `APPLE_CERTIFICATE` and `APPLE_CERTIFICATE_PASSWORD` are intentionally **not** exported to `GITHUB_ENV` so that Tauri does not attempt to resolve them through `tauri-macos-sign`.
  - The `Set up macOS code signing` step decodes the base64 `.p12` and imports it into a dedicated user keychain (`alloy-signing.keychain-db`), unlocks it with a 6-hour timeout, configures the key partition list (`apple-tool:,apple:,codesign:`) so `/usr/bin/codesign` can sign without interactive authorization prompts, and sets this keychain as the default and first entry in the user search list.
  - It trusts the public root certificate (`.github/macos-signing-cert.pem`) for code signing in `/Library/Keychains/System.keychain`.
  - It exports `TAURI_CONFIG={"bundle":{"macOS":{"signingIdentity":"Alloy Release Signing"}}}` to `GITHUB_ENV`.
  - Tauri sees the configured signing identity and the absence of `APPLE_CERTIFICATE`, invokes `/usr/bin/codesign` directly against the default keychain search list, and signs the app bundle with the stable identity.
- **Apple Developer ID path (`APPLE_CERTIFICATE` and `APPLE_ID` set):**
  - All Apple secrets (`APPLE_CERTIFICATE`, `APPLE_CERTIFICATE_PASSWORD`, `APPLE_ID`, `APPLE_PASSWORD`, `APPLE_TEAM_ID`, `APPLE_SIGNING_IDENTITY`) are exported to `GITHUB_ENV`.
  - Tauri's built-in `tauri-macos-sign` flow runs normally, importing the certificate to a temporary keychain, resolving the Team ID, signing, and submitting to Apple's notarization servers.
- **Ad-hoc fallback (no certificate configured):**
  - If no certificate secret is present, neither `APPLE_CERTIFICATE` nor `TAURI_CONFIG` is set, preserving `tauri.conf.json`'s default ad-hoc signing (`signingIdentity: "-"`).

#### Important: This is NOT Notarization
This self-signed certificate is strictly for establishing a **stable local code identity** across updates to eliminate repetitive keychain access prompts; **it is not notarization**.

Because the certificate is self-signed and not issued by Apple:
- macOS Gatekeeper will still present the standard "unidentified developer" warning when a user downloads the DMG or tarball directly from GitHub and opens it for the first time. Users must right-click -> "Open" (or approve in System Settings -> Privacy & Security -> "Open Anyway").
- In-app updates delivered via Alloy's built-in updater plugin (verified with `TAURI_SIGNING_PRIVATE_KEY` minisign signatures) do not trigger Gatekeeper warnings on replacement, and preserve keychain access across updates.
- Real Apple notarization requires an Apple Developer Program membership ($99/year). If acquired, setting `APPLE_ID`, `APPLE_PASSWORD`, and `APPLE_TEAM_ID` alongside the official Developer ID certificate in repository secrets will automatically enable notarization without modifying the workflow.

#### Key management
- Public certificate: `.github/macos-signing-cert.pem` (expires October 2036).
- Secrets: `APPLE_CERTIFICATE` (base64 `.p12`), `APPLE_CERTIFICATE_PASSWORD`, `APPLE_SIGNING_IDENTITY` (`Alloy Release Signing`).
- Private key backup: Stored in `~/.alloy-updater/macos-signing/` alongside the Tauri updater keys. If the private key is lost or replaced, the code signing requirement changes and users will receive one more keychain prompt on the following update.
### Android Release Signing

## 5. Android Keystore Creation & Management

No release keystore is checked in. Until the four secrets above exist, `scripts/sign-android-apk.sh` signs with a throwaway key (`CN=Alloy Test`) and warns; such an APK installs, but every build has a different signature, so Android refuses in-place updates. `v0.2.9` is the last release built that way — 0.2.9 testers have to uninstall it before installing a stably signed build, after which updates work normally.

### Creating a Production Keystore
Generate the key once, on a trusted machine, with Java 17+ (`keytool`). It must never be regenerated: a different key means Android treats the app as a new package.
```bash
keytool -genkeypair -v \
  -keystore alloy-release.jks \
  -alias alloy \
  -keyalg RSA -keysize 4096 \
  -validity 10000 \
  -storetype PKCS12 \
  -dname "CN=Alloy, O=Alloy, C=US"
```

Back the file up offline (password manager or encrypted volume) together with both passwords. Losing it means every installed user has to uninstall before the next update.

### Encoding for GitHub Secrets
Convert the keystore file to base64 for the `ANDROID_KEYSTORE_BASE64` secret:
```bash
# macOS
base64 -i alloy-release.jks | tr -d '\n' > alloy-release.jks.b64

# Linux
base64 -w 0 alloy-release.jks > alloy-release.jks.b64
```

Set all four secrets with the `gh` CLI, so nothing passes through the shell history of a shared machine:
```bash
gh secret set ANDROID_KEYSTORE_BASE64 < alloy-release.jks.b64
gh secret set ANDROID_KEYSTORE_PASSWORD   # prompts, or --body
gh secret set ANDROID_KEY_ALIAS --body alloy
gh secret set ANDROID_KEY_PASSWORD        # prompts, or --body
```

Then delete the base64 file and the plaintext keystore from the machine that is not the offline backup.

### Verifying the next build
Every release APK is signed by `scripts/sign-android-apk.sh`; the CI log no longer prints the throwaway warning, and this prints the release certificate:
```bash
apksigner verify --print-certs alloy-android.apk
```
The release certificate is `CN=Alloy, O=Alloy, C=US` with SHA-256
`FB:43:2F:8B:62:F1:57:1E:40:EF:3C:50:64:CD:C8:17:03:A8:78:8E:CF:3D:9B:0B:E9:C2:2D:62:82:E8:1A:B4`
(first proven on the 2026-10-29 nightly, APK SHA-256 `56ab510b…709c7`). Record it in the release notes; two consecutive releases signed with the same key are what make in-place Android updates possible.

## 6. Android Sideloading Instructions

Users installing Alloy on Android outside Google Play (via GitHub Releases or Nightlies) must sideload the APK.

### Prerequisites
1. Enable **"Install Unknown Apps"** in Android Settings for your browser or file manager (`Settings` → `Apps` → `Special App Access` → `Install Unknown Apps`).
2. Download `alloy-android.apk` (or `alloy-android-nightly.apk`) and corresponding `SHA256SUMS`.

### Installation via ADB (Developers)
```bash
# Connect device or launch emulator
adb devices

# Install APK (replace existing without losing app data)
adb install -r alloy-android.apk
```

> **Note on Signature Conflicts:**  
> Android forbids installing a release-signed APK over a debug-signed build (or vice-versa) with error `INSTALL_FAILED_UPDATE_INCOMPATIBLE`. To switch build types:
> ```bash
> adb uninstall vn.hce.alloy
> adb install alloy-android.apk
> ```
>
> **0.2.10 renamed the Android application id from `chat.alloy` to `vn.hce.alloy`.** The old id is a different app to
> the OS: `adb install -r` fails with `INSTALL_FAILED_UPDATE_INCOMPATIBLE`, so users must uninstall `chat.alloy` once
> before installing 0.2.10. That uninstall deletes the app-private directory `/data/user/0/chat.alloy`, including the
> local E2EE store; there is no data migration, so the device signs in again and re-verifies. The Matrix account data
> (`chat.alloy.prefs`, `chat.alloy.room_note`, `chat.alloy.room_tags`) and the keyring service names are unchanged and
> come back from the server after login. Desktop data does not carry over either: the identifier also selects
> `$APPDATA/vn.hce.alloy`, `$APPLOCALDATA`, `$APPCACHE` and `$APPLOG`, so 0.2.10 starts with an empty local store, a cold
> media cache and no local read marks. The old `chat.alloy` directories are left in place, not deleted.

## 7. Checksum & Integrity Verification

Every release publishes `SHA256SUMS` alongside the binary assets. Users and package managers should verify asset integrity prior to installation.

### Linux
```bash
sha256sum -c SHA256SUMS --ignore-missing
```

### macOS
```bash
shasum -a 256 -c SHA256SUMS
```

### Windows (PowerShell)
```powershell
Get-FileHash -Algorithm SHA256 .\Alloy_*_x64-setup.exe
# Compare hash with value listed in SHA256SUMS
```

## 8. Release Execution Checklist

When cutting a new stable release (e.g. `v0.2.2`):

1. **Write the release notes.** Add a `## 0.2.2 (pre-release)` section to `CHANGELOG.md` and commit it.
   This is the only file edited by hand for a release.
2. **Run one command** from a clean, up-to-date `main`:
   ```bash
   just release 0.2.2        # same as: scripts/release.sh 0.2.2
   ```
   It bumps the `Cargo.toml` version and `Cargo.lock`, pushes `chore(release): bump to 0.2.2`, waits
   for CI to pass on that exact commit, and only then pushes the tag. If CI fails it stops without a
   tag; fix the problem and run it again.
3. **The server re-checks everything.** The `Release gate` job of `release.yml` (`scripts/verify-release.sh`)
   runs before anything is built or uploaded, whoever pushed the tag. It requires: a `vX.Y.Z` tag equal
   to the `Cargo.toml` version, no second copy of the version in `tauri.conf.json` or `package.json`, a
   `CHANGELOG.md` section for it, a commit on `main`, and a green `ci.yml` run for that exact commit
   (it does not wait: if CI is still running or red the job fails at once, and you re-run it once CI is
   green; `release.sh` does the waiting before it tags). A failing check stops the release with the
   reason in the log. Run it by hand to preview: `scripts/verify-release.sh v0.2.2`. The tag is a plain
   lightweight tag; signing is not required.
4. **Monitor the release workflow** to completion.
   - Verify all desktop bundles (macOS DMG, Windows installer, Linux AppImage/deb) and the signed Android
     APK are attached to the release.
   - Inspect the SBOMs (`alloy-sbom-*.json`) and `SHA256SUMS`.
   - `https://github.com/centopw/alloy/releases/download/updater-feed/latest.json` must report the new version.
