## Triage rule (agreed before this audit)

- **Release blocker:** contrast on primary flows, or an unusable screen-reader experience on core
  flows.
- **Wave 2:** everything else, in the order recommended at the end.
- Severity here follows that rule. Two findings are blockers; one further finding (A11Y-03) is
  recommended for blocker status because WCAG 1.4.4 is AA and applies to every mobile user.

## How this audit was done

1. **Static review** of every shipped Svelte component under `apps/alloy/ui/src/lib/components`,
   the route shell (`routes/+layout.svelte`, `+page.svelte`), `app.html`, `tokens.css`,
   `layout.css`, `mobile.css` and the generated theme tokens. Interactive patterns were checked
   against the WAI-ARIA Authoring Practices (dialog, menu, listbox, tablist, radiogroup, toolbar,
   combobox).
2. **Computed contrast** from the real token values in `theme/generated/themes.css`, using the
   WCAG 2.1 relative-luminance formula, for every foreground/background pair the components
   actually spend. Thresholds: 4.5:1 for text, 3.0:1 for non-text (focus rings, UI boundaries).
   Composite cases (own-bubble meta, translucent chrome) are composited before measuring.
3. **Existing guards run** (they protect naming, controls, tokens, density, emoji and native-menu
   behaviour):

   ```
   cd apps/alloy/ui
   ./node_modules/.bin/vitest run src/lib/tokens-audit.test.ts src/lib/controls-audit.test.ts \
     src/lib/tooltip-audit.test.ts src/lib/density-audit.test.ts src/lib/emoji-guard.test.ts \
     src/lib/native-menu-audit.test.ts
   # Test Files  6 passed (6)
   # Tests       16 passed (16)
   ```

4. **Limitations.** No NVDA/VoiceOver/TalkBack session and no Android hardware were available in
   this environment. Screen-reader conclusions are code-level evidence plus reproducible steps;
   they must be confirmed on hardware before P2 sign-off (see Follow-ups). axe-core/Lighthouse
   cannot validate the virtualized conversation experience or announcement timing, which is why
   the audit is manual and code-based rather than a single automated score.

## Release blockers

### A11Y-01 · Avatar initials fail contrast in every non-light theme

- **Screen:** room list rows, message avatars, member/user lists — every avatar rendered with
  initials (users without a picture).
- **Severity:** Blocker (contrast on primary flows).
- **Owner:** FE.
- **Evidence:** `Avatar.svelte:110` paints initials with
  `color: var(--alloy-color-text-on-accent)` (white in all themes) on
  `background-color: {userColor}`. The dark/AMOLED/midnight palettes are light pastels
  (`themes.css`), so white initials land between **1.67:1 and 2.98:1**. Measured:
  `user-3 #fbbf24` = 1.67:1, `user-4 #4ade80` = 1.74:1, `user-12 #22d3ee` = 1.81:1 in every
  non-light theme. `alloy-light` passes because its palette is dark.
- **Repro:** launch with `alloy-dark` (the fallback when the system is not light), open a room with
  a sender who has no avatar; inspect the initials (white) on the avatar fill and measure with a
  contrast checker. Repeat with `alloy-amoled` and `midnight-ocean`.
- **Acceptance:** initials meet ≥4.5:1 against their own avatar fill in every compiled theme,
  verified by an automated contrast test. Either add an explicit per-user `on-color` (light text on
  dark fills, dark text on light fills) or choose the text colour by luminance. This likely needs
  an additive theme token, so the exact shape is a maintainer/theme decision.

### A11Y-02 · Conversation is not screen-reader operable

- **Screen:** conversation (all viewports), including history and incoming messages.
- **Severity:** Blocker (unusable screen reader on a core flow).
- **Owner:** FE.
- **Evidence:**
  - The timeline is a virtual list: `Timeline.svelte:3` imports `VList` from `virtua/svelte`;
    only the mounted window of rows exists in the DOM and in the accessibility tree. Rows render
    as plain `<div class="cell">` / `<div class="row">` with no list/listitem semantics
    (`Timeline.svelte:261-280`, `MessageRow.svelte:554-555`).
  - There is no live region for incoming messages. The conversation's existing live regions cover
    typing, the error toast, the selection count and live location (`Timeline.svelte:299`,
    `TypingIndicator.svelte:26`, `LiveLocationBanner.svelte:14`); a new message is never announced.
  - The scroll container is `role="presentation"` with pointer/wheel/touch handlers and no
    tabindex (`Timeline.svelte:255`), so assistive tech has no scrollable, named region to move
    through history.
- **Repro:** with VoiceOver (macOS) or TalkBack (Android), enter a room and navigate the
  conversation. Only the currently mounted rows are readable; scrolling the window replaces the
  readable content; send a message from another client and nothing is announced. Switching to
  browse mode offers no list structure.
- **Acceptance:** a documented screen-reader model for the timeline, verified manually on VoiceOver
  and TalkBack: (a) the conversation is a named region with list semantics where practical;
  (b) new incoming messages produce one polite announcement (sender + short preview), with a
  user-visible mute for chatty rooms; (c) history is reachable without a pointer (keyboard can move
  the virtual window, or a non-virtualized accessibility fallback exists). Announcement strategy is
  a design decision — do not "fix" this by making every rendered row live.

## Major

### A11Y-03 · Pinch zoom is disabled app-wide on mobile

- **Screen:** all mobile views.
- **Severity:** Major. **Recommend release blocker** — WCAG 1.4.4 (Resize Text) is AA and this
  removes the user's own remedy entirely; PM to confirm against the wave-1 triage rule.
- **Owner:** FE.
- **Evidence:** `app.html:6` sets `maximum-scale=1, user-scalable=no` in the viewport meta, which
  removes pinch zoom for the mobile WebView target.
- **Repro:** open Alloy on Android (or any mobile browser target); pinch out on a conversation.
  The page does not zoom. Repeat at 200% system font size — body text still cannot be enlarged by
  pinch.
- **Acceptance:** no `maximum-scale`/`user-scalable=no` restriction; layout remains usable at 200%
  zoom (no clipped composer, no overlapping chrome) on the phone layout; verified on Android and in
  a mobile browser viewport.

### A11Y-04 · Message actions are unreachable from the keyboard

- **Screen:** conversation, default bubbles layout.
- **Severity:** Major (keyboard baseline #20).
- **Owner:** FE.
- **Evidence:** a message row is a non-focusable `<div class="row">`
  (`MessageRow.svelte:554-555`). Its action bar is hidden by default —
  `.toolbar { visibility: hidden }` (`MessageRow.svelte:1177`) — and is only revealed by
  `.row:hover` or `.row:focus-within` at `(min-width: 900px) and (hover: hover)`
  (`MessageRow.svelte:1240-1255`). In the bubbles layout an own message or a grouped message has no
  focusable descendant (avatars are only rendered for some non-own rows), so `:focus-within` can
  never match and Tab skips the bar. There is no row-level `tabindex` and no keyboard path to the
  row context menu (`Shift+F10` has no target).
- **Repro:** desktop, bubbles layout. Open a room and press Tab from the composer backwards/forwards.
  Own messages and grouped messages never expose Reply/Edit/Delete; pressing the context-menu key
  on a message does nothing. The only reachable message controls are reaction chips, thread chips,
  or the avatar of certain received messages — depending on the content.
- **Acceptance:** with keyboard only, a message can be focused (a roving-tabindex message cursor or
  one "message actions" entry per row), Enter/Space/`Shift+F10` opens the action menu, and focus
  returns to the message after closing. A run of 200 messages must not add hundreds of tab stops —
  the design must use roving focus or a single entry point per row.

### A11Y-05 · Conversation cannot be scrolled from the keyboard

- **Screen:** conversation.
- **Severity:** Major.
- **Owner:** FE.
- **Evidence:** the document is pinned (`routes/+layout.svelte:32-42`: `html, body { position: fixed;
  overflow: hidden }`). The only scroll container is the timeline viewport, which is
  `role="presentation"` with no `tabindex` and no keyboard handler (`Timeline.svelte:255`).
  Scrolling is wired to pointer/wheel/touch only.
- **Repro:** desktop, focus the composer, press `PageUp`/`ArrowUp` with no text selected. Nothing
  scrolls. With focus on a room row, same result. History is only reachable with a pointer or by
  tabbing to a focusable element inside a rendered message.
- **Acceptance:** the conversation scroll region is keyboard-operable (focusable, named region that
  responds to arrows/PageUp/PageDown/Home/End, including loading older messages at the top), without
  depending on a pointer; verify in a keyboard-only pass.

### A11Y-06 · No skip link and two tab stops per room

- **Screen:** desktop room list → conversation.
- **Severity:** Major.
- **Owner:** FE.
- **Evidence:** the desktop shell renders the space rail, the room list and `<main>` with no skip
  link (`AdaptiveShell.svelte`; `grep -ni skip` finds none in the shell). Each room row is a
  `<button class="row">` plus a separate `<button class="more">` (`Sidebar.svelte:411`, `:467`), so a
  list of 60 rooms is roughly 120 tab stops before the conversation.
- **Repro:** load a workspace with ≥20 rooms, focus the first control, then Tab towards the message
  field. Every room costs two stops; no "skip to conversation" appears first.
- **Acceptance:** the first Tab stop offers "Skip to conversation" (and to the room list where
  useful), or the room list adopts a roving tabindex with arrow-key movement; the conversation is
  reachable in at most a few Tab presses regardless of room count.

### A11Y-07 · Phone pane switches lose focus

- **Screen:** mobile room list ↔ conversation.
- **Severity:** Major.
- **Owner:** FE.
- **Evidence:** selecting a room sets `pane = 'chat'` (`AdaptiveShell.svelte:232-233`); CSS then
  hides the list with `display: none` (`AdaptiveShell.svelte:680-682`). No focus is moved into the
  chat and none is restored on Back (`backToList`, `AdaptiveShell.svelte:242-249`). Focus therefore
  falls back to `body` when the focused room row is hidden. Screen-reader reading position is also
  lost.
- **Repro:** phone layout with a hardware keyboard or TalkBack. Focus a room row, activate it, then
  press Back (or the header back button). After opening the chat, Tab starts from the top of the
  document; after returning, focus is not on the room that was open.
- **Acceptance:** opening a chat moves focus to the room heading or the composer; Back returns focus
  to the originating room row; verified with keyboard and TalkBack.

### A11Y-08 · Composer is permanently announced as a combobox

- **Screen:** conversation composer (with or without the mention picker open).
- **Severity:** Major.
- **Owner:** FE.
- **Evidence:** the multiline `<textarea>` always carries `role="combobox"` with
  `aria-autocomplete="list"` and `aria-expanded={pickerOpen}` (`Composer.svelte:721-727`). When no
  mention popup is open this replaces textbox semantics with a collapsed combobox; the controlled
  listbox pattern is only partially implemented (the popup does not expose a full combobox
  contract).
- **Repro:** with VoiceOver/NVDA, focus the message field with no `@` typed. It is announced as a
  combo box with a collapsed popup instead of a multi-line text field.
- **Acceptance:** with no mention popup, the field is announced as a multi-line text field; if the
  combobox role is kept, the full combobox pattern is implemented consistently (expanded state,
  active descendant, listbox ownership) and mention navigation is verified with a screen reader.

### A11Y-09 · Error text fails AA on light canvas and dark panels

- **Screen:** settings sections, dialogs, onboarding, composer — every `.error` message.
- **Severity:** Major (contrast; not classified as a primary-flow blocker because most errors appear
  inside settings/dialogs, but it is widespread).
- **Owner:** Backend (token) + FE (usage).
- **Evidence:** components color `.error` with `var(--alloy-color-status-error)` at 12-13px.
  Measured against the surfaces errors actually sit on:

  | Theme | Pair | Ratio |
  | --- | --- | --- |
  | alloy-light | `#dc2626` on canvas `#f2f4f7` | **4.38:1** |
  | alloy-dark | `#ef4444` on panel `#1a1f2b` | **4.38:1** |
  | alloy-dark | `#ef4444` on elevated `#242a38` (dialogs/menus) | **3.81:1** |

  The theme's own checker does not test these pairs (see A11Y-14).
- **Repro:** dark theme, open a dialog that can show an inline error (e.g. a failing confirm or an
  invalid settings value) and measure `.error` text against the dialog surface; repeat in light
  theme with any error rendered on the canvas.
- **Acceptance:** error text is ≥4.5:1 on every surface it can appear on, in all compiled themes,
  enforced by the theme checker. Prefer a dedicated text token (e.g. `color.status.error.text`)
  rather than darkening the status colour used for dots/icons.

### A11Y-10 · `midnight-ocean` muted text fails on every surface

- **Screen:** all screens while the shipped `midnight-ocean` theme is selected — timestamps, meta,
  placeholders, secondary hints.
- **Severity:** Major.
- **Owner:** Backend (theme values).
- **Evidence:** `#64748b` against that theme's surfaces:

  | Surface | Ratio |
  | --- | --- |
  | panel `#111c3a` | **3.53:1** |
  | subtle / elevated `#1c2541` | **3.17:1** |
  | hover `#253256` | **2.64:1** |
  | bubble other `#1c2541` | **3.17:1** |
  | canvas `#0b132b` | **3.86:1** |

  The theme is offered in Appearance and reports `passes_aa: true` because the muted-on-panel pairs
  are not in the checker.
- **Repro:** Settings › Appearance › Midnight Ocean, then inspect any room-list timestamp or meta
  line; measure `#64748b` on the row surface.
- **Acceptance:** muted text ≥4.5:1 on canvas, panel, subtle, elevated, hover and received bubbles in
  this theme, enforced by the theme checker.

### A11Y-11 · Unread badge fails AA on the phone tab bar

- **Screen:** mobile tab bar (Chats badge), with unread count > 0.
- **Severity:** Major.
- **Owner:** FE.
- **Evidence:** `.badge` uses `background: var(--alloy-color-status-mention)` with
  `color: var(--alloy-color-text-on-accent)` at 11px (`MobileTabBar.svelte:143-144`). White on the
  mention colour measures **3.68:1** in `alloy-dark`/`alloy-light`/`alloy-amoled` (`#3b82f6`) and
  **2.14:1** in `midnight-ocean` (`#38bdf8`). The count is duplicated in the tab's `aria-label`, so
  screen-reader users still get it; the visual badge does not meet AA.
- **Repro:** phone layout, receive unread messages, measure the badge text over the tab bar surface.
- **Acceptance:** badge text ≥4.5:1 in every theme (e.g. use `accent-fill`, which passes, or a darker
  mention fill); verified by the automated contrast check.

## Minor

### A11Y-12 · Link text below 4.5:1 on subtle/hover surfaces

- **Screen:** surfaces that use `surface-subtle` / `surface-hover` under link text (settings chips,
  room-info notices).
- **Severity:** Minor.
- **Owner:** Backend (token thresholds/values).
- **Evidence:** `alloy-light` `#2563eb` on `surface-subtle #eaeef3` = **4.44:1**, on
  `surface-hover #e4e9ee` = **4.23:1**. The theme checker validates link text at **3.0:1**
  (`resolver.rs`, `text_link_on_canvas`), below WCAG 1.4.3's 4.5:1 for normal-size text.
- **Repro:** light theme, inspect a link rendered on either surface and measure.
- **Acceptance:** link text ≥4.5:1 wherever it is used, and the checker's link threshold raised to
  4.5 (keeping a documented 3.0 exception only for genuinely large text, if any).

### A11Y-13 · Own-bubble meta fails in `midnight-ocean`

- **Screen:** conversation, own messages (time/ticks).
- **Severity:** Minor.
- **Owner:** Backend (token).
- **Evidence:** `tokens.css:176` derives `--alloy-bubble-own-meta` as 82% of the own-bubble text over
  the bubble fill, with a comment requiring 4.5:1 at 11px. Measured: alloy-light 4.78:1,
  alloy-dark/amoled 5.03:1, but **midnight-ocean 3.81:1** (`#d1e7f2` on `#0077b6`).
- **Repro:** select midnight-ocean, send a message, measure the time/ticks inside the own bubble.
- **Acceptance:** own-bubble meta ≥4.5:1 in every theme; the derived colour must be part of the
  theme check so a new theme cannot regress it.

### A11Y-14 · Theme contrast checker omits pairs the UI uses

- **Screen:** theme generator / CI (process defect, visible across the app).
- **Severity:** Minor (systemic: it lets A11Y-01/09/10/11/12/13 regress silently).
- **Owner:** Backend.
- **Evidence:** the checker validates 32 pairs (`resolver.rs`), including text on canvas/subtle,
  link at 3.0, bubbles and the user palette on canvas and received bubbles. It does **not** check:
  muted text on panel/subtle/hover; error text on canvas/panel/elevated; link text on
  subtle/hover; link text at 4.5; the avatar's `text-on-accent` against each user palette entry;
  the derived own-bubble meta; or the composited worst case of the translucent chrome/chat surfaces
  (80–92% panel/canvas over the aurora). `themes.json` therefore reports `passes_aa: true` for all
  four themes while A11Y-09/10/11 exist.
- **Repro:** run the generator and compare its failure list with the measured table in this audit.
- **Acceptance:** add the missing pairs above to the resolver's contrast report, raise the link
  threshold to 4.5 for normal text, include the avatar on-colour per palette entry, and regenerate
  `themes.json`; the generated summary must fail when any new pair is below threshold. Any check
  that needs a composited backdrop should use a documented worst-case backdrop value rather than
  ignoring the material.

### A11Y-15 · Quick switcher does not restore focus

- **Screen:** quick switcher (`Cmd/Ctrl+K`).
- **Severity:** Minor.
- **Owner:** FE.
- **Evidence:** on open it focuses the input (`CommandPalette.svelte:87`) and traps Tab, but captures
  no opener and restores nothing on close. `Modal`, `SettingsDialog`, `ProfileCardHost` and
  `MediaViewer` all restore focus; this dialog is the exception.
- **Repro:** focus a room row, press `Cmd/Ctrl+K`, then `Escape`. Focus is on `body`; the next Tab
  starts from the top of the document.
- **Acceptance:** closing the palette (Escape, backdrop, or selecting a result) returns focus to the
  element that opened it, or to the newly selected room's row when a result was chosen.

### A11Y-16 · Narrow profile and emoji sheets claim `aria-modal` without a trap

- **Screen:** phone profile sheet, phone emoji sheet.
- **Severity:** Minor.
- **Owner:** FE.
- **Evidence:** `ProfileCardHost.svelte:113` sets `aria-modal="true"` when narrow; the component
  restores focus and closes on Escape, but does not trap Tab. `EmojiPickerHost.svelte:134-135` also
  declares a modal dialog on the phone sheet without a Tab trap (it does restore focus).
  `aria-modal="true"` tells assistive tech the rest of the page is inert, which is not true here.
- **Repro:** phone layout, open either sheet, then Tab repeatedly; focus moves into the page behind
  the sheet.
- **Acceptance:** either trap Tab while the sheet is open (and keep Escape + focus restore), or set
  `aria-modal="false"` and verify the background is genuinely usable by keyboard and screen reader.

### A11Y-17 · Declared composite roles lack their keyboard pattern

- **Screen:** reactions sheet tabs, emoji picker tabs, poll answers.
- **Severity:** Minor.
- **Owner:** FE.
- **Evidence:**
  - `ReactionsSheet.svelte:46-56` and `EmojiPicker.svelte:355-368` declare `role="tablist"`/`tab`
    but give every tab a normal tab stop and implement no Left/Right (or Home/End) movement; the
    emoji picker reserves arrows for its emoji grid.
  - `PollView.svelte:37-48` declares `radiogroup`/`radio` (single-choice) on buttons but implements
    no roving tabindex or arrow-key selection; every answer is a tab stop.
- **Repro:** open the reactions sheet or a single-choice poll and press Tab/arrows. Each tab is
  individually tabbable; arrows do nothing.
- **Acceptance:** either implement the WAI-ARIA keyboard pattern (roving tabindex, arrows move
  selection, only the active tab/radio is in the tab order) or drop the composite roles and use a
  button group with `aria-pressed` where that better matches the behaviour.

### A11Y-18 · No `h1` in the signed-in shell

- **Screen:** all signed-in views.
- **Severity:** Minor.
- **Owner:** FE.
- **Evidence:** the shell's first heading is an `h2` (`ChatHeader.svelte:78`, sidebar scope
  `Sidebar.svelte:537`, "No conversation open" `AdaptiveShell.svelte:364`). Only onboarding and the
  "no engine" error page have an `h1`.
- **Repro:** with a screen reader's heading list, start at the top of a signed-in view. The outline
  begins at level 2 and the app/room has no top-level heading.
- **Acceptance:** exactly one `h1` per view (the active room name, or "Alloy"/the list title when no
  room is open), with panels and dialogs as `h2`+; verified with a heading outline.

### A11Y-19 · Window title never reflects the active room

- **Screen:** all signed-in views.
- **Severity:** Minor.
- **Owner:** FE.
- **Evidence:** `app.html:7` sets a static `<title>Alloy</title>`; there is no `document.title`
  assignment anywhere in the UI source.
- **Repro:** open several rooms; the window/tab title stays "Alloy". In a screen reader's window
  switcher all rooms are indistinguishable.
- **Acceptance:** the title follows the active room (and reflects unread state when backgrounded),
  e.g. `Room — Alloy`; verified in the task switcher and with a screen reader.

### A11Y-20 · Avatar presence is not exposed to assistive tech

- **Screen:** avatars that render a presence dot.
- **Severity:** Minor.
- **Owner:** FE.
- **Evidence:** the avatar root is `role="img"` with `aria-label={effectiveAlt}`
  (`Avatar.svelte:116`), and the presence dot is a child span with `aria-label="Status: …"`
  (`Avatar.svelte:141`). A `role="img"` makes its descendants presentational, so the presence label
  is not exposed. The inner `<img>` also repeats `alt={effectiveAlt}`, so the name can be announced
  twice in some AT/browser combinations.
- **Repro:** with VoiceOver, navigate to a user avatar whose presence is online. Only the name is
  announced; the status is missing.
- **Acceptance:** presence is part of the avatar's accessible name (e.g. "Mai, online") or exposed
  once as a separate status element outside the `role="img"`; the avatar name is announced once.

### A11Y-21 · Listbox options contain interactive buttons

- **Screen:** quick switcher results.
- **Severity:** Minor.
- **Owner:** FE.
- **Evidence:** `CommandPalette.svelte:176-195` puts `<button>` elements inside
  `<li role="option">`. ARIA options must not contain focusable/interactive descendants; keyboard
  handling is already done on the input via `aria-activedescendant`, so the buttons are redundant
  for keyboard and can confuse AT.
- **Repro:** inspect the palette's accessibility tree; options expose nested buttons.
- **Acceptance:** options contain only presentational content (or use a different, valid pattern);
  the input keeps `aria-activedescendant`, arrow/Enter behaviour and click-to-choose.

### A11Y-22 · Programmatic smooth scroll ignores reduced motion

- **Screen:** conversation (jump-to-latest, jump-to-mention, scroll-to-top).
- **Severity:** Minor.
- **Owner:** FE.
- **Evidence:** `Timeline.svelte:216` and `:236` call
  `vlist?.scrollToIndex(..., { smooth: true })`. This is JS-specified smooth scrolling, which the
  CSS `scroll-behavior: auto !important` in the reduced-motion rules cannot override. Other
  JS-driven motion is correctly guarded (`MediaViewer.svelte:84`, `MessageRow.svelte:320`).
- **Repro:** enable "Reduce motion" in the OS, open a long room, press the jump-to-latest button
  while scrolled up. The list still animates.
- **Acceptance:** smooth scrolling is only requested when
  `matchMedia('(prefers-reduced-motion: reduce)').matches` is false; verified with the OS setting and
  each of the three jumps.

## Covered and passing

- **Reduced motion:** `tokens.css:391-422` and `mobile.css:93-109` collapse animation/transition
  durations globally for `prefers-reduced-motion` and for the app's own `data-reduced-motion` flag;
  every looping animation also has an explicit reduce guard (sidebar spinner, voice pulse, upload
  sweep, changelog bar, media skeleton, typing dots, audio pulse, sending pulse, onboarding pulse);
  the media viewer and message swipe consult `matchMedia`. Only A11Y-22 remains.
- **Dialog focus:** `Modal` (trap, Escape, focus restore), `SettingsDialog` (trap, Escape, restore,
  Back handling), `MediaViewer` (trap, Escape, arrow navigation, restore), quick switcher (trap,
  Escape), profile card (Escape, restore), emoji picker (Escape, restore). Gaps: A11Y-15/16.
- **Naming:** 199 `aria-label` uses across components; the tooltip guard test enforces an accessible
  name for every icon-only control; decorative `Icon`s are `aria-hidden`; form fields go through
  `TextField`/`TextArea`/`Select` with labels (settings pass `for`/`id`, radio cards use
  `fieldset`/`legend`, the switch is the Bits UI primitive).
- **Live regions:** errors are `role="alert"`; connection, typing, permissions, saves and uploads
  use `role="status"`/`aria-live`; uploads expose `aria-valuenow`/`aria-valuetext`; the voice
  recorder keeps its elapsed time out of announcements (`aria-live="off"`).
- **Touch targets:** `--alloy-touch-target: 44px` applies to buttons, tabs, menu items, selects and
  text fields on coarse pointers (`mobile.css:15,49-65`); the switch gets a 44px hit area; emoji
  cells/tabs are 44px on phones; the mobile tab bar is 56px. Inline links inside message bodies are
  exempt by design (WCAG 2.5.8 permits inline exceptions; the 24px minimum applies to standalone
  controls).
- **Semantics:** dialogs declare `role="dialog"` + `aria-modal` + labels; context menus implement
  `menu`/`menuitem`, arrow keys, Home/End and roving focus; the segmented control implements
  `radiogroup` with roving tabindex and arrows; the panel resizer is a keyboard-operable
  `separator`; polls expose `aria-checked`. The keyboard gaps are A11Y-17.
